# glyphviz_core — shipped feature notes

Loaded when working under `glyphviz_core/` (Qt-free engine, loaders, topology, channels). Moved verbatim from the root `CLAUDE.md` "Feature Status" on 2026-10-18; the root keeps a one-line index of each entry. Project-wide rules (collaboration notes, data contract, tech stack) stay in the root file.

- **Channels (animation)** — time-series animation of node attributes via the `ch-map`/`ch-tracks` CSV pair (`gv_` native, `np_` for GaiaViz-format files), with a playback transport, FPS control, and a dense-scene fast path. Powers the EEG, GPS, IoT, and biometric examples. Native spec: `glyphviz-skill/references/channels-animation.md`. The bindable-attribute set lives in one table, `channel_engine.py`'s `_ATTR_TO_FIELD`, and covers transform + rates + color + palette (`palette_id`/`color_index`, resolved to RGB per frame) + shape (`ratio`/`topo`/`geometry`/`mesh_id`) + visibility (`hide`/`show_text`) + the World row's scene settings (`render_mode`, `fog_*`, `tag_font_size`, and background via its own `color_r/g/b`). Adding one is a `_ATTR_TO_FIELD` entry plus, if it re-places children, an `_TRANSFORM_FIELDS` entry. **Channel In (2026-08-28)**: the node↔channel join (`ch_input_id`, in `node.extras`, not a Node field) is editable from the Properties panel — a "Channel In" spin box + hint label under Texture ID, applying to the whole selection. `channel_engine.set_channel_id()` writes back through whichever of `_CH_INPUT_KEYS` the file already used (channel_id_of reads the FIRST present, so adding a second spelling would leave two disagreeing columns); `channel_attrs()` answers "what will this channel do", filtered through `_ATTR_TO_FIELD` exactly as `load` filters. `MainWindow._ch_rebind()` re-resolves live: **reset() BEFORE load()**, because `load()` snapshots current field values as the ones `reset()` will later restore, so rebinding mid-playback without resetting bakes that frame into the scene permanently. MainWindow now keeps `_ch_map`/`_ch_tracks`/`_ch_id_to_col` alongside the engine for this. `_ch_load_from_csv` deliberately **no longer requires `engine.has_bindings`** — a channel file no node points at yet is precisely the scene this field exists to wire up, and hiding the transport left nothing to bind against. Tests: `tests/test_channel_binding.py` (helpers + the reset-then-reload ordering) + `tests/test_channel_binding_gui.py` (real MainWindow, headless).
- **Topology Scale (2026-08-12)** — `Node.topo_scale`, a per-PARENT multiplier on exactly the translate axes that node's topology reads as a **distance** rather than an angle. The axis classification is one table, `topology.LINEAR_PLACEMENT_AXES`, and the entire feature is a pre-multiply applied in two places that consult it (`_batched_topo_offsets` for both batched engines, `scale_linear_axes` for the scalar `placement_offset` the gizmo differentiates) — the `_*_offset` functions are untouched and stay the readable per-topology spec. Angular axes are never scaled, so no value can distort a circular layout; World Grid children and roots are exempt. **Default 1.0 = one translate unit is one world unit** (GlyphViz's original behavior AND the load default for a missing column, so all 53 example files and every user file are byte-identical and render unchanged — verified). `node.TOPO_SCALE_ANTZ` (1/180) reproduces ANTz's convention where a linear axis spans the parent's own extent (360 units across a cube facet), the setting at which a degrees-authored layout survives a switch between an angular and a linear topology — this is what fixes the reported bug (Sphere→Cube threw children 2997 units from a radius-9 parent; at 1/180 they stay within 19). GUI: Properties panel "Topo Scale" row under Topology — spin box + log slider + `1:1`/`ANTz` presets, applying to the whole selection (so Select By > Topology > Cube then one drag retunes every cube parent). Presets write the exact constant rather than routing through the 6-decimal spin box. Bindable as a Channels attribute (`_ATTR_TO_FIELD` + `_TRANSFORM_FIELDS`). A topology change that leaves a child >20x its parent's radius away fires a status-bar hint naming the field (`Scene.worst_child_placement_ratio` → `MainWindow._hint_scattered_children`) — only for parents still at the default, since a tuned value isn't a mistake. Drag sensitivity divides k out per-axis (`viewport._move_axis_divisors`). Tests: `tests/test_topo_scale.py` (math, per-topology, table-driven off LINEAR_PLACEMENT_AXES) + `tests/test_topo_scale_gui.py` (widget wiring, headless). Docs: `glyphviz-skill/references/topologies.md`, `glyphviz-docs/docs/reference/topologies.md`. The Properties panel and the Glyph Composer share the range + log-slider mapping via `glyphviz_gl/topo_scale_ui.py` — the same drag has to mean the same thing in both, since a composed glyph is edited in the panel afterwards. `main_window` re-exports those under the `_TOPO_SCALE_*` / `_topo_scale_to_slider` names its tests already use.
- **Glyph Composer Topo Scale auto-fit (2026-08-13)** — `LevelSpec.topo_scale` + `LevelSpec.topo_scale_auto` (`glyphviz_core/glyph_recipe.py`), stamped onto generated nodes by `generate_nodes`. The Composer describes child placement in ONE vocabulary — DIST_ANGULAR always hands the next level `translate_x = 0..360` — but the parent's topology decides whether that is degrees or world units, so picking Cube/Pin/Plane/None threw children ~300x the parent's radius away (Jeff's 2026-08-13 report). `suggested_topo_scale()` returns TOPO_SCALE_ANTZ exactly when a 0..360 sweep is about to be read as a distance (child level is DIST_ANGULAR **and** `LINEAR_PLACEMENT_AXES[topo][0]`), else 1.0; `effective_topo_scale()` picks between it and the user's number. GUI: a "Topo Scale" row under Topology in the per-level form (spin + log slider + 1:1/ANTz, mirroring the Properties panel) plus an **Auto** checkbox, default on. Touching the value or a preset takes the level off Auto — the control reached for IS the decision. **Its handlers write straight into the LevelSpec; `_save_params` deliberately does NOT read the row back**, because the 6-decimal spin box would silently round the ANTz preset from 1/180 to 0.005556 on the next preview tick. Templates predating the fields load onto Auto (that's what rescues the broken ones). **`hyperglyph_lab/hyperglyph_generator.py` takes the same fit** (Jeff asked for it 2026-08-13 after seeing the Composer result): its pool is named `ANGULAR_SAFE_TOPOS` but contains `TOPO_PIN`, which reads translate_x as HEIGHT, so an angular level under a Pin parent was a 360-unit vertical smear. Pin is the *only* cause — all 67 re-fitted levels across a 200-design sample were Pin levels, at every depth, moving 62 designs (31%) and pulling them in 7.5x–117x. A pre-2026-08-13 recipe JSON has no `topo_scale` keys, so it reloads onto the fit and regenerates as the corrected design. Tests: `tests/test_glyph_composer_topo_scale.py`.
- **Compact CSV save (2026-09-07)** — `save_node_csv` writes the **minimal native dialect** by default: the 22 base columns (the 20 the loader requires, plus `ratio` and `facet`) plus only the columns the scene's data needs. Measured on the LIDAR example's full 442,767-point scan: **243.4 MB → 40.7 MB** (550 → 92 bytes/row), save 18.3 s → 4.2 s, reopen 9.8 s → 6.3 s; across all 80 example scenes, 630 MB → 145 MB (**4.4x**). The rule is the one the old writer already used for its extension columns, now applied to every column: **a column is written only when omitting it would make some node reload as a different value.** So a column whose values are all covered by a documented load default is dropped — including 60-odd `extras` columns of zeros carried in from a previously-94-column file — and a save/reload cycle is column-stable rather than column-accreting. Deliberately matches GlyphViz Web's `writeGvNodeCsv` (`glyphviz-web/src/gv/writeNodeCsv.ts`), which already wrote this dialect; the two apps now produce the same file for the same scene. **Two deliberate divergences from web**, both pure size wins that web could adopt: floats are written at 6 dp with **trailing zeros trimmed** (`_num`; `0.000000` is eight bytes to say `0`, and that padding was most of the file — this alone is ~1.4x of the total), and a value that rounds to zero is normalized to `0` rather than `-0` (an epicycle generator's `cos(90°)` lands on -1.2e-17; `-0` also made the writer **non-idempotent**, since pandas reads that cell back as a positive zero — caught by re-saving all 80 examples twice and comparing bytes). Unknown third-party `extras` columns are now **carried verbatim**, which the 94-column writer silently dropped (it only ever wrote columns with a slot in its own layout) — so a GaiaViz file's `np_ch_in_id` survives a round trip. Two `extras` columns mirror the node's id and are dropped when they do: `record_id` (the tag join key, which falls back to the node id) and `data` (ANTz's id mirror, which nothing reads). The 94-column layout stays available as `save_node_csv(..., compact=False)` → `_save_node_csv_antz`, unchanged; no GUI surface, since ANTz write-compatibility is no longer a goal. Tests: `tests/test_compact_csv_save.py` — the per-column rules on synthetic nodes, plus the **all-80-scene** column-stability sweep that replaces the old `sorted(examples)[0]` guard in `test_tag_font_size.py` (it costs ~30 s; the suite went 32 s → 66 s).
- **Imported meshes: UVs, crease normals, and the meshes/ folder (2026-09-17)** — three gaps in `GEO_MESH` closed together, because none of them is much use alone. (1) **UVs survive import.** `MeshData.uvs` + `_extract_uvs`; `register_mesh` bakes `glTexCoord2f` into the SAME display list (a texcoord is ignored while GL_TEXTURE_2D is off, so no `_tex_lists` twin is needed), and `draw()`'s GEO_MESH branch — which used to `return` before `textured` was even computed — now binds when `_mesh_uv[mesh_id]`. A mesh with NO UVs stays untextured **even when the node sets `texture_id`**: every vertex would inherit the current texcoord and smear one texel over the model, which is visibly worse than the flat colour. UV seams survive `validate=True` because trimesh's `merge_vertices` won't weld two co-located vertices carrying different UVs — that is also the only reason a generator ever duplicates a position. (2) **Crease-angle normals.** `load_mesh_file` welds duplicates, so `mesh.vertex_normals` averaged every face at a corner and **a cube arrived as 8 vertices all pointing (0.577, 0.577, 0.577)** — every imported hard-surface model shaded like a beach ball, STL worst. `_crease_normals` returns per-CORNER normals `(M,3,3)` averaging only faces within `DEFAULT_CREASE_ANGLE` = **40°** of their own, area-weighted; `MeshData.normal_for()` falls back to per-vertex when it returns None (degenerate mesh, or a fan hub that would blow the padded incidence table past 40M entries). Vectorized via a padded (V,K) incidence table — 82k faces in 0.34 s; a per-vertex Python loop costs minutes. A cylinder gets a round barrel AND hard caps *at the same shared rim vertices*, which is the thing per-vertex normals structurally cannot do. (3) **`meshes/` folder.** `Viewport.load_mesh_folder` + a hook in `_load_csv_path` beside the existing `media/` one: **mesh_id = the file's 1-based position in the sorted folder**, exactly `texture_id`'s rule. Before this a mesh_id meant "the Nth file imported by hand this session", so a GEO_MESH scene **could not be reopened, let alone shipped** — that is why no mesh example existed until now. A file that fails to parse is **skipped but still consumes its id**, or every later mesh shifts by one and the scene opens wearing the wrong shapes. `tools/export_frame.py` loads the folder too (it otherwise renders every model as the sphere fallback and says nothing). **Creases are decided on POSITION, not vertex index**: the two sides of a UV seam are separate vertices by construction, and indexing the incidence table by vertex gave each side only its own faces to average — a hard shading stripe down a perfectly smooth lofted tube. Fixed by grouping corners on rounded position; GlyphViz Web merges the same way, and once it matched the two apps agreed on a 1,812-tri airframe to **0.05 deg mean / 0 median / 0.21 max** (float32 noise) where the seam corners had differed by up to 14 deg. **Sort is by NAME as a plain string, not by Path**: pathlib compares case-INSENSITIVELY on Windows and case-sensitively elsewhere, so `sorted(iterdir())` handed out different mesh_ids per OS. (media/ -> texture_id still sorts Paths and is deliberately left alone — changing it would renumber textures in shipped scenes.) Tests: `tests/test_mesh_textures.py` (18) + `tests/test_mesh_folder.py` (10) + `tests/test_meshkit_mirror.py` (6). Docs: `glyphviz-docs/docs/reference/imported-meshes.md`; skill: `node-csv-format.md`'s `mesh_id` row + `textures-and-media.md`.
- **Multi-material model import (2026-09-18)** — an OBJ carrying N `usemtl` groups imports as **one node per material** under one hidden rig, instead of collapsing to a single shape wearing one texture. Prompted by Jeff downloading a cargo-ship model whose 16 materials and 6 texture sets GlyphViz could only render light grey. Core is Qt-free: `mesh_loader.load_mesh_parts()` (returns `MeshPart`, or **`[]` when there is no split to exploit**, so callers fall back to `load_mesh_file` without special-casing), `parse_mtl()`, `find_mtl()`, and `glyphviz_core/model_import.py` (texture resolution, asset writing, node building), shared by the GUI and `tools/model_to_scene.py`. GUI: Meshes > **Import Model with Materials…**, deliberately a SEPARATE action — plain Import Mesh File is untouched, since "give me this shape" and "give me this model" are different questions and folding them would rewrite existing scenes under their authors. **Two scales, and confusing them is the classic bug**: a `MeshPart.mesh` is in WHOLE-model units (node scale 1), but a part *written to its own file* is reloaded re-normalized onto its OWN bbox — so a file-route node needs `scale = part.radius`, or every part arrives the same size (a cockpit as large as its hull). Both routes are pinned against the real `node_world_matrix` in `tests/test_model_import.py`. **mesh_id and texture_id are folder POSITIONS**, so an import that inserts files renumbers the scene underneath itself — `model_import.remap_ids()` carries existing nodes across **by file name**, snapshotting both folders before the write; without it a loaded scene silently wears the wrong images AND the wrong shapes. Rig gets `rotate_x = 90` (`Y_UP_RIG_ROTATION`): DCC tools export Y-up, GlyphViz is Z-up, and the un-rotated model reads at a glance as a failed import rather than as a ship standing on its tail. Three traps the format itself sets: **(a)** a V-Ray/Arnold/Redshift OBJ export routinely has **no `map_Kd` and `Kd 0 0 0` on every material** (the shading lived in a node graph `.mtl` cannot carry) — believing it imports a black silhouette, so `MaterialSpec.is_black` falls back to neutral grey; **(b)** the `mtllib` name and the shipped file name drift apart (this model recorded `Cargo Spaceship.mtl` beside `Cargo_Spaceship.mtl`), which a strict lookup turns into a silently uncoloured import — `find_mtl` + `_LooseResolver` match case/space/underscore-insensitively, and the resolver is needed too or trimesh names every part `material_0` and the association is lost; **(c)** with NO resolvable `.mtl` the split still works but the part NAMES are trimesh's file-derived ones, pinned by a test. `tools/model_to_scene.py` writes a whole scene folder and carries the Maya-specific recovery (**deliberately not in the app**): `--maya-scene` walks `file<N>.ftn -> .oc -> <shader>.dc -> <SG>.ss`, which works because Maya names exported materials after their shadingEngine = the `usemtl` name. It also recovers `VRayLightMtl.cl`, the emissive parts, lifted to full brightness since GlyphViz has no emitter. Jeff's ship: 16 parts, 12 textured, 11 images, **reassembly exact to 0.0**. **Overlapping copies (found 2026-09-18 when Jeff reported "two ships overlapping", ribbed z-fighting, one copy complete-but-wrong-material and one correct-but-missing-engines)**: the SAME export habit that loses textures also writes the model out repeatedly — an object-level material assignment plus per-face-set ones — so the OBJ shipped **87,128 triangles for 24,830 of actual surface** (3.5x), each copy with its OWN vertex indices, so an index-level duplicate check sees nothing (verified: 0 duplicates by index, 62,298 by POSITION). `_dedupe_across_parts` keeps each distinct triangle surface once, from the material with the FEWEST faces (narrow assignment = specific intent, catch-all = leftover); a broad material still keeps whatever it covers ALONE, which on this ship was exactly the **3,340 engine triangles** no per-material assignment claimed — that is the half Jeff saw missing. Keyed on SORTED rounded positions, so a reversed twin counts as one surface (fine: GEO_MESH draws with culling off). `dedupe=True` default, `MeshPart.dropped_faces` reports it, never silent; `--keep-overlaps` on the tool. Import also got 1.7x faster. Also fixed here, and **older than this feature**: `load_mesh_file` died on `ModuleNotFoundError: networkx` for any mesh whose winding is already INCONSISTENT — trimesh's `validate=True` calls `fix_normals`, whose `fix_winding` needs networkx (an optional dep this project does not carry) and early-returns only when winding is already consistent, which is why most models never hit it. Now degrades via `_validate_without_winding` (keeps the duplicate/degenerate-face removal that kills NaN spike hubs; loses only the winding repair, costing some faces their outward normal). Installing networkx would restore it fully — Jeff's call, it is a packaging decision. Tests: `tests/test_model_import.py` (29) + `tests/test_model_import_gui.py` (6, headless). Docs: `glyphviz-docs/docs/reference/imported-meshes.md`.
- **Scene merge** — File > Merge Node CSV… (Ctrl+M) loads a second node file (and its companion tag file) *into* the loaded scene instead of replacing it, rebasing ids and every id-bearing `extras` field (`parent_id`, a link's `child_id`, the tag join key `record_id`). `glyphviz_core/scene_merge.py`. Channel animation from the merged file is deliberately not imported — that's the known gap if it ever comes up.
