# GlyphViz — Project Context for Claude

## Vision and Goals

GlyphViz is **not** a straight reimplementation of ANTz or GaiaViz. The goal is to match both tools as a foundation, then go beyond them with new capabilities. Examples already shipped: `TOPO_PLOT` (line plots, GPS, oscilloscope data) and `TOPO_SURFACE` (deformable grids, FFT, LIDAR, sound spheres). The Spiral topology was independently derived — no GaiaViz source code is available, only the reference documentation bundled in this repo.

## Feature Target: ANTz vs GaiaViz

Two different questions, with two different answers — don't collapse them:

- **Data contract** (what to generate/validate): `glyphviz-skill/references/` is authoritative for GlyphViz's own native `gv_` format. Consult it first for anything producing data. See "GaiaViz Skill vs. GlyphViz Skill" below.
- **Behavior** (how a topology, placement, or interaction should act): `gaiaviz-skill/references/` is the source, since GlyphViz aims to match ANTz/GaiaViz semantics. For features absent from both (Spiral, Plot, Surface), derive from first principles.

**The ANTz 94-column layout is not GlyphViz's data contract.** `save_node_csv` still *writes* those 94 columns (plus GlyphViz extension columns appended after them) so saved files stay readable by ANTz/GaiaViz tooling, and `load_node_csv` reads them — but that is a compatibility write format, not an authoring requirement. Native `gv_` data needs only the ~20 required columns `glyphviz-skill/references/node-csv-format.md` documents; everything else has a documented load default.

**Key constraint:** We do not have access to the GaiaViz GitHub source. Never assume undocumented GaiaViz behavior — only what the reference docs describe.

## File Naming Convention

GaiaViz's `np_` file/column prefix stands for "neural physics," Shane Saxon's architectural concept underpinning ANTz/GaiaViz — GlyphViz has no equivalent architecture and shouldn't claim the name. GlyphViz's own example/generated data uses a `gv_` prefix instead (`gv_node.csv`, `gv_tag.csv`, `gv_ch-map.csv`, `gv_ch-tracks.csv`). The `np_` prefix is still recognized when *reading* genuine third-party GaiaViz files — both as a filename pattern and as the handful of GaiaViz-specific column names (`np_node_id`, `np_geometry_id`, `np_topo_id`, `np_texture_id`, `np_ch_in_id`) aliased in `glyphviz_core/csv_reader.py` and `channel_engine.py`. Do not rename those aliases — they exist for interop, not branding. `gaiaviz-skill/examples/` also keeps `np_` since it demonstrates the actual GaiaViz spec.

**Node↔tag pairing convention**: a tag CSV's name is its node CSV's name with the `node`/`np_node` stem swapped for `tag`/`np_tag` — e.g. `gv_node.csv` ↔ `gv_tag.csv`, `np_node.csv` ↔ `np_tag.csv`, and timestamped saves carry the same stamp on both (`gv_node20260625182432.csv` ↔ `gv_tag20260625182432.csv`). `glyphviz_core/csv_reader.py`'s `stamp_node_and_tag_paths()` derives the tag path this way and only when the unstamped node-file stem ends in `node`; `load_node_csv` looks for the matching tag file automatically on open. Tag rows: `table_id` is always `0`, `record_id` matches the node CSV's `id` column (full row format and the three `title` encodings: `glyphviz-skill/references/tags-and-labels.md`).

## Feature Status

**Shipped** — these were listed here as pending long after they landed; verified against the code 2026-07-24. Don't re-propose them as new work:

- **Tags** — text labels attached to nodes, loaded either from inline `text`/`link` columns or a companion tag CSV (`gv_tag.csv` native, `np_tag.csv` for GaiaViz-format files), with URL, local-file, and app-launch link encoding (U key / Alt+click). Per-node `show_text` pins a label on regardless of the scene-wide tag settings; the World node's `tag_color_mode` / `tag_color_r/g/b` / `tag_font_size` style every label. **Tag Text Size (2026-08-18)**: `Node.tag_font_size`, another World-row scene setting on the same pattern as the colors — Properties > Display slider (6-36 pt), read by `Viewport._tag_font_size()` (which clamps, since a Channels track or a hand-edited CSV can put anything in the field) and applied in the one place both the mono and stereo tag passes build their painter, `Viewport._tag_painter()`. `TAG_DEFAULT_FONT_SIZE` = **11**, raised from the 9 pt labels were hardcoded to (Jeff found that too small); it is also the load default, so every existing scene simply gets bigger type with no file change — and since the column is only written when != 11, all 53 examples stay column-stable. Bindable as a Channels attribute. Tests: `tests/test_tag_font_size.py` (the last one measures real painted ink through `_paint_tags`, so the setting is pinned to actual pixels, not just to a number moving between objects). Native spec: `glyphviz-skill/references/tags-and-labels.md`. `gaiaviz-skill/references/format/Tag-Format.md` covers only the legacy `np_` companion-file dialect — reach for it when reading genuine GaiaViz files, not when generating.
- **Channels (animation)** — time-series animation of node attributes via the `ch-map`/`ch-tracks` CSV pair (`gv_` native, `np_` for GaiaViz-format files), with a playback transport, FPS control, and a dense-scene fast path. Powers the EEG, GPS, IoT, and biometric examples. Native spec: `glyphviz-skill/references/channels-animation.md`. The bindable-attribute set lives in one table, `channel_engine.py`'s `_ATTR_TO_FIELD`, and covers transform + rates + color + palette (`palette_id`/`color_index`, resolved to RGB per frame) + shape (`ratio`/`topo`/`geometry`/`mesh_id`) + visibility (`hide`/`show_text`) + the World row's scene settings (`render_mode`, `fog_*`, `tag_font_size`, and background via its own `color_r/g/b`). Adding one is a `_ATTR_TO_FIELD` entry plus, if it re-places children, an `_TRANSFORM_FIELDS` entry.
- **Save edits back to CSV** (timestamped node+tag save, K key) and **multi-select**.
- **Transform gizmo (red/green/blue X/Y/Z handles)** — arming Move/Rotate/Size draws arrows/rings/bars on the first selected visual node; dragging one constrains the edit to that axis and tracks the cursor, and the whole selection takes the same field change (GlyphViz Web's multi-select rule). Purely **additive**: a press that misses every handle still gets the pre-existing free-form axis-checkbox drag, so nothing was replaced. View > Show Transform Handles hides them without disarming the mode. The Properties panel's "Lock X/Y/Z together" checkbox also governs Size mode (`Viewport.uniform_scale`): any Size drag then applies one FACTOR to all three axes — deliberately not the panel spin boxes' equalize-the-values rule, which would flatten a 3:1:1 glyph to a cube on the first pixel. Rotate rings are built perpendicular to their OWN axis (`gizmo.perpendicular_basis`), never spanned by the other two — the gizmo's three rotation axes are non-orthogonal in general, and spanning ring A with axes B and C squashed it to a sliver near gimbal lock (Jeff's 2026-08-03 report); coincident rings now correctly *mean* gimbal lock. Suppressed on Links, in Camera Mode, and in stereo. The per-mode handle frames are the whole point and are NOT the node's local axes: Move follows the numerical gradient of `topology.placement_offset` (so a Sphere parent's red arrow is the longitude tangent), Rotate differentiates the rotation matrix (so HTR's `rotate_y`→Z-rotation is handled), Size uses the world_basis columns. Qt-free math in `glyphviz_core/gizmo.py`; tests `tests/test_gizmo.py` (math, pinned against the real engine) + `tests/test_gizmo_viewport.py` (interaction, no GL context needed — camera matrices are seeded and checked against a real paint). Docs: `glyphviz-docs/docs/reference/viewer-navigation.md#transform-handles`.
- **Camera Mode (free flight)** — **C** toggles it (this *displaced* the old plain-C camera cycling, which moved to **Shift+C**; reverse-cycling is gone, the Camera toolbar covers direct jumps). Left-drag is ANTz-style **rate flight** on ANTz's opposite button (reworked 2026-07-30 at the test group's request, replacing the original per-move drag with transient banking — banking is gone entirely): the press point becomes a bearings origin, the held cursor offset from it sets a continuous forward/back speed and turn rate (integrated per repaint tick in `_apply_fly_drag`, so motion continues while the mouse sits still; 3px dead zone), and flight is locked to the horizontal plane it starts on (translation follows the heading with pitch dropped). Right-drag looks around from where the camera stands (ANTz's left-button gesture), both buttons slide, wheel flies. Same orbit rig underneath: flight holds `_cam_distance` fixed and moves the *target* end of the arm (`_reaim_about_eye`, `_translate_rig` in `viewport.py`), so the target rides in front of the camera instead of pinning it. Locked axis cameras can't fly; Follow Selected is cleared on entry. Tests: `tests/test_camera_mode.py`.
- **Drag and drop** — dropping a node CSV, a scene folder, or a **zip** onto the window loads it; Shift+drop merges instead of replacing. Also takes `.pdb`, mesh files, and image/video folders. All routing decisions live in the Qt-free `glyphviz_core/drop_router.py` (`resolve_drop()` returns an ordered `DropPlan`; `MainWindow.apply_drop()` executes it), so they're testable headlessly — `tests/test_drop_router.py`. A folder/zip drop only ever *actions* the node CSV: the tag file, ch-map/ch-tracks pair, audio manifest, and `media/` textures are all discovered from that path by the existing loaders. Node CSVs are identified by **columns, not filename**, so arbitrarily-named files load and companions never masquerade as scenes. Zips extract beside themselves (never overwriting an existing folder), falling back to temp when that's unwritable; entries with absolute or `..` paths are refused. Docs: `glyphviz-docs/docs/reference/drag-and-drop.md`.
- **Fetch Basemap** — World Grid panel button (flat grids only): measures the grid children's lon/lat bounding box, downloads map imagery for that window from a free tile service (OSM streets / Esri satellite / OpenTopoMap terrain — no API key), reprojects Web Mercator → plate carrée so the map lines up with child placement, stamps the required attribution into the corner, writes `media/zz_basemap_grid<id>.png` beside the CSV, and sets the grid's extents + `texture_id` (other nodes' `texture_id`s auto-shift when the insertion changes media numbering; refetch overwrites in place, no shift). Qt-free logic in `glyphviz_core/basemap.py` (tile cache in `%LOCALAPPDATA%\GlyphViz\tile_cache`, 60-tile cap per fetch); dialog+worker in `glyphviz_gl/basemap_dialog.py`; tests `tests/test_basemap.py` run offline with an injected fetcher. Antimeridian-crossing windows unsupported. Docs: `glyphviz-docs/docs/reference/basemaps.md`.
- **Minimum glyph size is now opt-in (2026-08-11)** — GlyphViz's earliest commits clamped every glyph's rendered scale (`scale_* × base_scale`) to **0.2 per axis** so a near-zero-scale node stayed clickable, which silently overrode authored data at every one of the three places draw scale is built. The clamp is now `Scene.scale_floor`, **default 0.0 (off)**, switchable at runtime via `Viewport.enforce_scale_floor` ← the Properties panel's Global Scale group checkbox and View > Enforce Minimum Glyph Size (both surfaces sync through `MainWindow._set_scale_floor`). Constant: `scene.DEFAULT_SCALE_FLOOR`. If a new code path computes rendered scale it must read `scene.scale_floor` — do NOT hardcode 0.2 again; the three existing paths (`_bake_draw_data`, `_bake_draw_rows`, `node_world_matrix`) plus the viewport's `_radius_of` framing hint are pinned against each other in `tests/test_scale_floor.py`. World Grid footprints stay exempt whatever the setting. Authoring guidance is unchanged (keep visible scales ≥ 0.2) so a scene reads the same with the option either way — that's why no example needed rebalancing.
- **Topology Scale (2026-08-12)** — `Node.topo_scale`, a per-PARENT multiplier on exactly the translate axes that node's topology reads as a **distance** rather than an angle. The axis classification is one table, `topology.LINEAR_PLACEMENT_AXES`, and the entire feature is a pre-multiply applied in two places that consult it (`_batched_topo_offsets` for both batched engines, `scale_linear_axes` for the scalar `placement_offset` the gizmo differentiates) — the `_*_offset` functions are untouched and stay the readable per-topology spec. Angular axes are never scaled, so no value can distort a circular layout; World Grid children and roots are exempt. **Default 1.0 = one translate unit is one world unit** (GlyphViz's original behavior AND the load default for a missing column, so all 53 example files and every user file are byte-identical and render unchanged — verified). `node.TOPO_SCALE_ANTZ` (1/180) reproduces ANTz's convention where a linear axis spans the parent's own extent (360 units across a cube facet), the setting at which a degrees-authored layout survives a switch between an angular and a linear topology — this is what fixes the reported bug (Sphere→Cube threw children 2997 units from a radius-9 parent; at 1/180 they stay within 19). GUI: Properties panel "Topo Scale" row under Topology — spin box + log slider + `1:1`/`ANTz` presets, applying to the whole selection (so Select By > Topology > Cube then one drag retunes every cube parent). Presets write the exact constant rather than routing through the 6-decimal spin box. Bindable as a Channels attribute (`_ATTR_TO_FIELD` + `_TRANSFORM_FIELDS`). A topology change that leaves a child >20x its parent's radius away fires a status-bar hint naming the field (`Scene.worst_child_placement_ratio` → `MainWindow._hint_scattered_children`) — only for parents still at the default, since a tuned value isn't a mistake. Drag sensitivity divides k out per-axis (`viewport._move_axis_divisors`). Tests: `tests/test_topo_scale.py` (math, per-topology, table-driven off LINEAR_PLACEMENT_AXES) + `tests/test_topo_scale_gui.py` (widget wiring, headless). Docs: `glyphviz-skill/references/topologies.md`, `glyphviz-docs/docs/reference/topologies.md`. The Properties panel and the Glyph Composer share the range + log-slider mapping via `glyphviz_gl/topo_scale_ui.py` — the same drag has to mean the same thing in both, since a composed glyph is edited in the panel afterwards. `main_window` re-exports those under the `_TOPO_SCALE_*` / `_topo_scale_to_slider` names its tests already use.
- **Glyph Composer Topo Scale auto-fit (2026-08-13)** — `LevelSpec.topo_scale` + `LevelSpec.topo_scale_auto` (`glyphviz_core/glyph_recipe.py`), stamped onto generated nodes by `generate_nodes`. The Composer describes child placement in ONE vocabulary — DIST_ANGULAR always hands the next level `translate_x = 0..360` — but the parent's topology decides whether that is degrees or world units, so picking Cube/Pin/Plane/None threw children ~300x the parent's radius away (Jeff's 2026-08-13 report). `suggested_topo_scale()` returns TOPO_SCALE_ANTZ exactly when a 0..360 sweep is about to be read as a distance (child level is DIST_ANGULAR **and** `LINEAR_PLACEMENT_AXES[topo][0]`), else 1.0; `effective_topo_scale()` picks between it and the user's number. GUI: a "Topo Scale" row under Topology in the per-level form (spin + log slider + 1:1/ANTz, mirroring the Properties panel) plus an **Auto** checkbox, default on. Touching the value or a preset takes the level off Auto — the control reached for IS the decision. **Its handlers write straight into the LevelSpec; `_save_params` deliberately does NOT read the row back**, because the 6-decimal spin box would silently round the ANTz preset from 1/180 to 0.005556 on the next preview tick. Templates predating the fields load onto Auto (that's what rescues the broken ones). **`hyperglyph_lab/hyperglyph_generator.py` takes the same fit** (Jeff asked for it 2026-08-13 after seeing the Composer result): its pool is named `ANGULAR_SAFE_TOPOS` but contains `TOPO_PIN`, which reads translate_x as HEIGHT, so an angular level under a Pin parent was a 360-unit vertical smear. Pin is the *only* cause — all 67 re-fitted levels across a 200-design sample were Pin levels, at every depth, moving 62 designs (31%) and pulling them in 7.5x–117x. A pre-2026-08-13 recipe JSON has no `topo_scale` keys, so it reloads onto the fit and regenerates as the corrected design. Tests: `tests/test_glyph_composer_topo_scale.py`.
- **Glyph Composer preview camera holds still (2026-08-13)** — `Viewport.set_nodes()` auto-frames, which is right on scene open and wrong on every keystroke in the Composer: zooming in on a detail and being yanked back to a distant overview on the next edit made close-up work impossible (Jeff's 2026-08-13 report). `_do_preview()` now snapshots `camera_state()` across the rebuild and `restore_camera_state()`s it. Re-framing is explicit: the **Reset View** button on the Preview header, a freshly-loaded template, and the first preview of all (`_camera_framed` guards that first one).
- **Camera smoothing (2026-08-14)** — optional ANTz-style navigation "inertia". `Viewport.camera_smoothing_tau` (seconds, **default 0 = off**) + `camera_smoothing_scope`, driven by the Properties panel's Camera group (slider + Off/ANTz presets + an "Applies to" combo). Requested by former ANTz users (the glide made demos look smoother) and, more importantly, because it buffers hand tremor — Dr. Warner reported Parkinson's patients benefiting from ANTz's version. **ANTz's actual mechanism, read from the source at `repos/antz/`**: two independent smoothers — a 10-cycle boxcar average of raw mouse deltas (`npUpdateMouse`, npmouse.c:162-195, every camera mode; the tremor filter) and a first-order low-pass on the camera's *world position* while "targeting" (`npCameraTranslate`, npengine.c:405-447), engaged by the L+R combo drag via `npSetCamTarget`. The second one is what Jeff disliked: ANTz eased POSITION while applying the orbit angle and zoom instantly the same frame, so the eye chased a solution the aim had already left and the orbited object swung out of frame for ~1.5s. GlyphViz fixes that by easing the whole rig **coherently** — azimuth, elevation, distance and target under one time constant — verified: the eye stays on its orbit sphere to 5.7e-14 through a full glide. The filter is `1 - exp(-dt/tau)`, exactly frame-rate independent (ANTz's `0.05*(65/(fps+5))` fudge is not, which is why its smoothing was heavier in its early slower years); the boxcar is deliberately NOT ported (pure latency + ringing, and it can't produce coast-to-rest). Architecture: `_cam_*` stays the ACTUAL rendered camera so **every reader is untouched** (matrices, picking, distance-scaled drag speeds); gestures write `_cam_goal_*` and end with `_settle_camera()`, which collapses goal onto actual unless smoothing covers that gesture — so tau=0 is bit-identical to the pre-feature code. Every gesture first calls `_adopt_direct_camera_writes()` (snap the goal from the actual **when settled**), which is what keeps code that assigns `_cam_*` directly — the Glyph Composer preview, several tests — working; mid-glide the goal wins instead (`_reconcile_camera_goal`). Programmatic moves (presets, `set_camera`, auto-framing, focus, flight, restore) snap via `_snap_camera_goal()`. **Follow Selected is the one exception and must stay one (fixed 2026-08-17):** it runs EVERY frame from `paintGL`, so calling `_snap_camera_goal()` there re-pointed the azimuth/elevation/distance goals at the lagging actual and erased any in-progress glide on the very next repaint — with smoothing on and F enabled the camera was locked solid (verified: 30 frames of orbit drag moved it 0.0°), and `_camera_settled()` reading True also released the repaint timer the glide needed. `_apply_follow_target` now writes the **pivot only**, to actual and goal together (still unsmoothed — following a moving node tracks a source, not a hand tremor), so orbit and zoom stay live exactly as the View menu promises. Pinned by `test_following_navigates_exactly_as_not_following`. **Camera Mode is excluded outright** — rate flight is already integrated per tick and re-derives the rig from the current eye, so a lagging actual would curve the flight path. A still-settling camera holds the repaint timer open (`_update_render_timer_state`) and releases it at sub-pixel tolerance (`is_settled`: 0.05° ≈ 1px at a 60° FOV; a tighter tolerance idle-spun the timer for 3s). Qt-free math in `glyphviz_core/camera_smoothing.py`; tests `tests/test_camera_smoothing.py` (filter math) + `tests/test_camera_smoothing_viewport.py` (wiring, incl. "off is off") + `tests/test_camera_smoothing_gui.py` (panel). Docs: `glyphviz-docs/docs/reference/viewer-navigation.md#camera-smoothing-optional-inertia`, `properties-panel.md`. **Session-only, and deliberately so** — Jeff considered making it a persisted user preference and decided against it for now (2026-08-14): "it is currently the only one, so let's keep it in the GUI." There is no QSettings anywhere in the app; revisit when a *second* user preference appears and that layer starts earning its keep, not before. Jeff verified the feature the same day; note that ANTz's **tiny settle tolerance** was his specific complaint ("it had to settle and lock before the camera could comfortably orbit"), so `is_settled`'s sub-pixel tolerance is the fix for the reported problem, not an incidental tuning choice. A left click/drag halting an in-progress glide is emergent (at the default combo-only scope a single-button orbit is unsmoothed, so it lands the glide immediately) and Jeff likes it — don't "fix" it.
- **Wrapped new-object placement + Placement Step (2026-08-14)** — ANTz's row-wrapping rule for auto-placed new objects, with the step exposed. `glyphviz_core/placement.py` (Qt-free): `wrapped_grid_offset(index, step)` places children by ordinal, `step_from(x, y, step)` places roots relative to the previous one, and the two walk the SAME lattice (pinned by a test that steps 200 times and compares) so a run of N and a run of Shift+N lay out identically. `translate_x` steps, and when the next step would reach `PLACEMENT_WRAP` (360 — one lap, i.e. the first object's slot on any circular topology) it restarts at 0 and `translate_y` takes the step instead: a Cartesian parent arrays into a grid, a Sphere/Torus/Cylinder parent starts a new ring instead of stacking. **ANTz's source rule** is `npNodeNew`, npnode.c:363-384 — `translate_x = -15 * siblings`, y bumped every 24 children (24 × 15 = 360). Two deliberate divergences: y is NOT folded back into -180..180 (ANTz did, npnode.c:378-384, and so eventually reused slots — GlyphViz keeps growing a taller grid), and the step is a GUI field instead of a hardcoded 15. GUI: Properties > Create > **Placement Step** spin box (`MainWindow._new_step` → `_placement_step()`), `DEFAULT_PLACEMENT_STEP` = **5.0**, which preserves the historical child spacing (and the guided tour's screenshots); the ROOT step therefore changed 10 → 5. Root placement also switched from `max(translate_x) + 10` to "one step on from the last root CREATED (highest id)" — after a wrap the largest x is back in the previous row — and now skips World Grids (a grid is the surface, not a member). Links (type 7) no longer consume a child slot. Five call sites share the two helpers: `_create_root_node`, `_create_child_node`, both `_paste_clipboard` branches, `_load_mesh_path`. Also in the same panel row group: **Placement Z**, the `translate_z` a new object is born with — TWO spin boxes (`_new_root_z` / `_new_child_z` → `_placement_z(is_child)`), defaults `DEFAULT_ROOT_Z` = 0.0 and `DEFAULT_CHILD_Z` = 5.0, deliberately not one field: the axis means height above the world plane for a root but offset off the parent for a child (radially outward on Sphere/Torus/Cylinder), so a root at 5 would hover off the grid while a child at 0 would sit INSIDE a topology-None parent. Tests: `tests/test_placement.py` (lattice math) + `tests/test_placement_gui.py` (real MainWindow, headless). Docs: `properties-panel.md#create`, `viewer-navigation.md`, guided tour §5/§8.
- **Save Selection (2026-08-14)** — File > Save Selection As… (Ctrl+Alt+S) writes the selected nodes to a node CSV of their own. **The whole feature exists because of one fact**: `topology._resolve_hierarchy` silently treats a node whose `parent_id` is absent from the file as a ROOT, and a root's `translate_x/y/z` IS its world position with no topology offset — so a naively-saved subset relocates everything (a Sphere child's lon/lat/altitude reloads as literal world XYZ; a World Grid child lands off the map). Qt-free `glyphviz_core/selection_export.py`, shaped like `scene_merge.py`: `plan_selection()` resolves membership without copying (so the dialog previews live on a 100k-node scene), `build_selection()` materializes. Membership = selection + descendant closure (checkbox, on; the `_delete_selected`/`_copy_selected` rule) + links with BOTH ends inside (auto-added even when unselected) + the type-0 World row (never bulk-selectable, carries the scene look). One-ended links are dropped (existing Copy/Paste + merge rule); `branch_level` is restated via `scene_merge.recompute_branch_levels` (promoted from private for this). **ids are preserved**, unlike merge's rebasing — `record_id` and channel bindings stay coherent for free. Three detach policies for a top node whose parent stayed behind, default **bake**: `translate` ← world position, `rotate`/`scale` ← decomposing `world_basis` into `R @ diag(s)`, written as `rotation_mode = EULER_XYZ`. **Exact, and here is why**: `world_basis = parent_basis @ child_local @ diag(scale)` is what every descendant composes off (own basis AND, through `offset_basis`, position) and is also the draw matrix over `base_scale` — preserve it and the entire subtree is pinned, rod cap offset and World Grid footprints included. Two reported (never hidden) limits: a rotated non-uniformly-scaled ancestor SHEARS the basis, which no rotate+scale pair expresses (`decompose_basis` returns a shear magnitude, `approximated_ids` counts it), and rates change frame of reference (`animated_detached`). A third is inherent to the format, not the code: the bake is exact only at the `base_scale` it ran at. Companions: tag CSV always (name convention via the new `csv_reader.companion_tag_path`/`unstamped_stem`), plus a filtered ch-map/ch-tracks pair (`channel_loader.export_channel_subset` filters at the FILE level so unparsed columns round-trip; channel ids from the new `channel_engine.channel_ids_for_nodes`). Deliberately NOT stamped with a timestamp — Save/Save As/K stamp because they snapshot a scene, this exports to a name you chose. GUI: `glyphviz_gl/save_selection_dialog.py` (options + live preview), `MainWindow._save_selection_as`. Tests: `tests/test_selection_export.py` (math + rules, incl. the round-trip fidelity check through real Scene objects) + `tests/test_selection_export_gui.py` (wiring, headless). Docs: `glyphviz-docs/docs/reference/save-selection.md`.
- **Link geometries (2026-08-15)** — a Link (type=7) renders whatever `geometry` it carries, stretched between its two ends, instead of only a line or a prism. **ANTz's own behavior, read from `repos/antz/sdk/src/io/gl/npgldraw.c:961` (`npDrawLink`)**: translate to A, `Rz(atan2(uy,ux) - 90°)·Rx(asin(uz) + 90°)`, `glScalef(ratio, ratio, distance × 0.5)`, then +1 unit along the axis — i.e. `npGLSurface` draws the node's ordinary geometry with a bespoke matrix. `ratio` is the thickness on **both** cross-axes (Jeff's call, and ANTz's — NOT scale_x/scale_y; a link's own translate/rotate/scale stay inert). Qt-free math in `glyphviz_core/link_geometry.py`. **One deliberate improvement over ANTz**: the glyph's *own* local Z extent is mapped onto the A→B segment (`local_z_span`), which is identical to ANTz's fixed `distance × 0.5` for every -1..1 shape and fixes Pin, whose apex is its local origin (ANTz papered over that with a conditional -1 nudge in npGLSurface, npgeometry.c:205, leaving a pin link hanging past its B-end). **Mode is chosen by `geometry` alone** — no new column, so a link's look travels with the CSV. `LINK_LINE_GEOMETRIES` = {27 Line, 28 Prism, **22 Point**}: Point is in there because a fixed-pixel sprite has no extent to stretch AND because it keeps the GTDB Org_Event_Network example's 6400 links rendering unchanged. That set is the entire back-compat surface — every example file uses 27/28/22. Glyph links are now pick-solid (same matrix as the visible pass) and draw a selection box; line/prism links keep their long-standing no-box behavior. **Same-day fix, and it is older than this feature**: `_render_pick_scene` drew a unit "fallback pick sphere" at `world_pos(link.id)` so a link with a missing B-end stayed clickable — but a link's own position IS its A-end's (translate 0,0,0, parent_id = the A-end), so that sphere sat exactly on a real node at that node's own scale and was drawn AFTER it. Cube and Octahedron are inscribed in the unit sphere, so it swallowed them: measured through the real pick FBO, an A-end node had **zero** pickable pixels; a Sphere node tied on depth and survived by luck, which is why Jeff experienced it as angle-dependent and had been working around it for sessions. The sphere bought nothing — when an end is unresolvable the visible pass draws nothing, so it let an INVISIBLE link outrank a visible node. ## Topology Inventory

All 18 types defined in `glyphviz_core/topology.py` are now implemented: None (0), Cube (1), Sphere (2), Torus (3), Cylinder (4), Pin (5), Rod (6), Point (7), Plane (8), Zcube (9), Zsphere (10), Ztorus (11), Zcylinder (12), Zrod (13), Spiral (14), Video (15), Plot (16), Surface (17).

The legacy ANTz/GlyphViz-native node CSV column for Cube's face selector is spelled `facet` (1-indexed: 1=+X, 2=-X, 3=+Y, 4=-Y, 5=+Z, 6=-Z — confirmed against a real ANTz session, see commit history); GaiaViz's `np_` dialect spells the same concept `subspace` (0-indexed). `glyphviz_core/csv_reader.py`'s `load_node_csv` checks for `subspace` first and falls back to `facet - 1`; `save_node_csv` always writes `facet` (the canonical ANTz column name) from `Node.subspace + 1`.

Z-topology variants (9–13) are each "akin to" their non-Z counterpart with the surface/radius offset term zeroed out (children sit through the center/axis rather than on the rendered surface) — see `Topology-Guide.md`'s "Important Scale and Position Notes" section. Zrod's placement math is intentionally identical to Zcylinder's.

When topology behavior is ambiguous, consult `gaiaviz-skill/references/structure/Topology-Guide.md` first. If not covered there, derive from first principles and note the choice in the commit message.

## World Grid (type=6)

Implemented 2026-07-13 (second attempt; the reverted V1's implicit root-glyph attachment is gone). A World Grid is a real, movable/rotatable/scalable node whose children attach **explicitly** via `parent_id = grid.id` — never implicitly, and scenes have no default grid (legacy type-6 rows in loaded files do render; GaiaViz's parent_id=0 main-grid convention is deliberately not used). Children place by `translate_x`=longitude, `translate_y`=latitude, `translate_z`=elevation within the grid's **extents window** (`Node.grid_extents()`), stored in the 94-column `trigger_lo_x/hi_x` (lon min/max) and `trigger_lo_y/hi_y` (lat min/max) fields; `segments_x/y` are the rendered cell counts. Degenerate (hi ≤ lo, i.e. legacy all-zero) axes fall back to the whole-earth window (-180..180, -90..90), which centers at (0, 0) so a grid at the origin with scale 1 is an exact 1:1 frame — a child at (180, 90) coincides with a non-child node at world (180, 90). Region windows recenter children on the window midpoint. The grid's draw matrix is extents half-spans × RAW scale (no base_scale, and never the optional minimum-glyph-size clamp — see `scene._grid_draw_scale`) so the rendered rectangle stays under its children.

Key rules: grid scale re-spaces child POSITIONS per axis but never child rendered size or subtree internal spacing (keyed on parent TYPE=6 in `compute_world_transforms` / `update_world_transform_rows` — plain topo=Plane parents keep legacy scale inheritance); grids are never click/rubber-band-pickable (G key selects/cycles them, matching ANTz; the node table and World Grid panel also select) and are excluded from bulk Select All; Move-drag sensitivity for children of scaled Cartesian parents divides by the parent's cumulative scale (`viewport._move_axis_divisors` — this was V1's "hypersensitive mouse" failure). Solid grid geometry (`GEO_GRID`) takes an equirectangular texture across the window; wire geometry draws the lattice only.

**Globe form**: a grid whose `geometry` is Sphere/Sphere Wire (`Node.grid_is_globe()`) renders as a globe and places the SAME children by KML lon/lat on the sphere surface (radius `GRID_GLOBE_RADIUS` = 180/π at scale 1, so the equator is exactly 360 world units — the flat 1:1 map rolled up; `translate_z` = radial elevation, children get TOPO_SPHERE's outward base rotation). Toggle via the World Grid panel's Shape combo or the Geometry dropdown (wire/solid preserved; flat↔globe is just a geometry change + invalidate, fully CSV-native). Extents recentering does not apply on a globe (absolute lon/lat; the panel disables those fields); `segments_x/y` set the graticule. The sphere is drawn bespoke in `viewport._globe_surface` with exact equirect UVs — do NOT swap in `gluSphere`, whose texture mapping is offset and mirrored in longitude vs KML. Solid grid surfaces (plate or globe) render into the pick FBO as color-ID-0 occluders: still unpickable, but clicks can't select glyphs hidden behind them; wire forms get no occluder.

## Rotation Convention

`rotate_x/y/z` support two interpretations, selected per-node via `Node.rotation_mode` (`glyphviz_core/node.py`):

- **`ROTATION_MODE_HEADING_TILT_ROLL`** (1) — ANTz's only-ever convention: a Z-X-Z "proper Euler" sequence borrowed from KML's Heading/Tilt/Roll camera-and-model convention (`rotate_y`=Heading about z, `rotate_x`=Tilt about x, `rotate_z`=Roll about z again — see `gaiaviz-skill/references/structure/Node-Field-Descriptions.md`'s Rotate section). Heading-then-Tilt is the standard spherical-coordinate parameterization, matching the longitude/latitude convention `translate_x/y` already use on Sphere/Torus topologies.
- **`ROTATION_MODE_EULER_XYZ`** (0) — GlyphViz-only, and the default for new nodes: `rotate_x/y/z` each rotate about their own named axis, intuitive for hand-posing glyphs. Jeff finds the ANTz convention unintuitive for that workflow and no longer needs rotation-specific ANTz file compatibility.

Implemented in `glyphviz_core/topology.py`'s `local_rotation_matrix()` dispatcher. **CSV default-handling is asymmetric by design**: a missing `rotation_mode` column (every pre-existing ANTz/GaiaViz/`gv_` file) loads as `HEADING_TILT_ROLL` in `csv_reader.py`'s `load_node_csv`, preserving old files' rendering exactly; a freshly-constructed `Node()` in code defaults to `EULER_XYZ`. `save_node_csv` only writes the column when a node's value would be *misread* by that load-side fallback (i.e. `rotation_mode != HEADING_TILT_ROLL`) — not simply "non-default" — so untouched legacy files stay byte-for-byte stable and new EULER_XYZ nodes still round-trip correctly. See `examples/Rotation_Convention_Example/` for a verified (numerically checked against `local_rotation_matrix()`) side-by-side demonstration: identical `(rotate_x=30, rotate_y=0..360)` input traces a level circle under Heading/Tilt/Roll but wobbles in elevation under Euler XYZ.

## GaiaViz Skill vs. GlyphViz Skill

Two separate Claude skills exist, for two separate formats — neither stands in for the other:

- **`glyphviz-skill/`** — the actively-maintained skill for GlyphViz's own **native** format (`gv_` prefix, only 20 required columns, no mandatory infrastructure rows). This is the skill Jeff shares externally, and `glyphviz-skill/references/` is the authoritative spec for GlyphViz's own CSV data contract — consult it first for anything generating or validating `gv_` data.
- **`gaiaviz-skill/`** — reference material for the actual legacy GaiaViz/ANTz format (`np_` prefix, 94 columns, mandatory infrastructure rows). Its role is interop and behavioral fidelity only: reading genuine third-party GaiaViz files, and grounding topology/behavior decisions in GaiaViz's documented conventions (see "Feature Target: ANTz vs GaiaViz" above). It is not the contract for anything GlyphViz generates natively — `glyphviz-skill/` is.
